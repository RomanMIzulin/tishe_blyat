# Работа над «Тише»

## Контекст

Рабочее приложение находится в `v1/`. Перед изменениями прочитай
[v1/README.md](v1/README.md), перед работой с интерфейсом и текстами —
[DESIGN.md](DESIGN.md). Этот файл задаёт правила разработки, README описывает
реализованное поведение, DESIGN — визуальный язык и голос сервиса.
Термины — в [GLOSSARY.md](GLOSSARY.md).

«Тише» — сервис, то есть услуга, а не самоцельный IT-продукт. Приложение —
способ её оказания. Сервис помогает замечать психологическое напряжение и находить подходящий способ
обойтись с ним в моменте. Это не требование успокоиться: иногда важны злость,
выражение несогласия или обозначение границы. Не обещай обязательное снижение
напряжения и не приравнивай спокойствие к успеху. Это не диагностика и не терапия.

## Стек и границы

- Интерфейс и логика — Elm. Не добавляй React, JSX, Next.js, React-компоненты или
  второй UI-runtime. Чужие рекомендации адаптируй к Elm и браузерным стандартам,
  а не переноси вместе с их стеком.
- `v1/src/Domain.elm` — чистая предметная модель и JSON-граница.
  `Main.elm` — Model/Msg/update/view, команды и подписки.
  `Theory.elm` — теоретические оптики, источники и оговорки.
- `v1/src/bridge.js` — минимальная граница браузерного IO через Elm ports.
  Не переноси в JS предметную логику и состояние интерфейса.
  `styles.css` — обычный CSS; переиспользуй существующие переменные и компоненты.
- Проверки: Elm-тесты в `v1/tests/`, JS Playwright и axe в `v1/e2e/`.
  Архитектурные правила elm-review и их тесты — в `v1/review/`;
  [границы проверок](v1/review/README.md). Не подавляй нарушения и не ослабляй
  политику ради прохождения: изменение границы требует явного решения и тестов.
  Не заводи параллельный Python-набор браузерных тестов. Используй версии
  инструментов из проекта, не меняй глобальные установки.

## Модель и эффекты

- Сначала определи типы и допустимые переходы. Взаимоисключающие состояния
  представляй union types, не сочетаниями булевых флагов и строк.
- Предметные вычисления делай чистыми; время и результаты IO передавай явно.
  Внешние данные проверяй декодерами. Сохраняй инварианты непрозрачных типов.
- Результат IO отражай отдельным событием; не объявляй сохранение или удаление
  успешным до подтверждения. Независимые эффекты объединяй через `Cmd.batch`,
  зависимые выполняй в нужном порядке; не добавляй поэлементное IO и логирование.
- Меняй минимально необходимое. Новые зависимости, смена хранения, backend и
  архитектурные переделки требуют отдельного согласования.
- Телесные практики — конкретные действия, не только наблюдение. Сохраняй
  видимые ограничения каждой практики; не добавляй давление на глаза,
  предписания боли/жжения или нагрузку на шею через свешивание головы.
  Основания и редакторские границы — в [docs/body-practices.md](docs/body-practices.md).

## Чувствительные данные

- Записи остаются на устройстве: без отправки серверу, аналитике, внешним AI
  или в логи. Не помещай заметки и ответы в URL. Для тестов и демонстраций
  используй только вымышленные данные.
- Текущее хранение — незашифрованный `localStorage`, ключ `tishe.entries.v1`.
  Не называй его зашифрованным или гарантированно приватным; экспорт тоже открыт.
- Сохраняй Web Locks и проверку снимка между вкладками. Не перезаписывай конфликт,
  повреждённые данные или неизвестную схему молча; не удаляй их ради «починки».
- Удаление требует подтверждения и обработки отказа. Смену схемы или ключа
  проектируй с учётом существующих записей; не выдавай потерю данных за миграцию.
  Черновики не сохраняй незаметно.

## Проверки и завершение

Команды ниже запускаются из корня проекта; нужен Node.js 22.12+:

```sh
npm --prefix v1 ci                 # установка по lockfile, если нужна
npm --prefix v1 run dev            # приложение на localhost:5173
npm --prefix v1 run check          # форматирование, тесты приложения и правил, review, build
npm --prefix v1 run test:e2e        # Playwright + axe, desktop и mobile Chromium
```

Для первого E2E-запуска может потребоваться установка Chromium:
`cd v1 && npx playwright install chromium`.

При изменениях логики добавляй или обновляй проверки поведения и граничных
состояний; при изменениях правил проверяй как нарушения, так и допустимый код.
При изменениях интерфейса запускай также E2E и проверяй затронутые
экраны на desktop и mobile. Axe не заменяет ручную проверку клавиатуры.
Скриншоты сейчас сохраняются, но автоматически с эталонами не сравниваются.

Для правок только документации достаточно проверить форматирование, ссылки
и соответствие команд проекту. Не редактируй вручную `dist/`, `elm-stuff/`,
`node_modules/` и `test-results/`. В результате укажи изменения, реально
выполненные проверки и оставшиеся ограничения; не называй непроверенное рабочим.

## Скиллы

Используй `elm-programming` для нетривиальной работы с Elm, `domain-modeling` —
когда меняются понятия и их связи. Документацию библиотек и внешние источники
ищи по необходимости, не перед каждой задачей. Не подключай набор скиллов
«на всякий случай» и не устанавливай новые без запроса. Эти правила не
отключают глобальные скиллы или расширения Pi.
